# CrowdFlow — Circuit Packs

Every Grand Prix circuit is a swappable data pack. This document specifies the format, the
circuit/event split, and the time-gated crossing model.

Rationale in [`decisions.md`](./decisions.md) D4 and D5, **revised by D6**.

All 23 rounds of the 2026 season are indexed in
[`../circuits/index.yaml`](../circuits/index.yaml), generated by joining the Jolpica calendar to
the f1-circuits geometry dataset. Silverstone is the seed circuit; the rest follow.

---

## 1. Imported, then refined

**Most of a circuit pack is imported, not typed.** D6 is the governing decision: the venue
structure is built from OpenStreetMap plus the official venue map *before* the event, because it
is the frame of reference everything else needs. Traces then refine it — they do not create it.

```
   IMPORTED  (before the event)             REFINED  (from traces, continuously)
   ────────────────────────────             ───────────────────────────────────
   circuit.yaml   identity, frame      →    desire lines the maps lack
   track.geojson  outline              →    real capacity from observed flow
   graph.yaml     OSM paths + barriers →    corrections where OSM is stale
   gates.yaml     barrier=gate         →    which crossings open, and when
   viewing.yaml   building=grandstand  →    sensing quality per zone
   crossings.yaml bridges, tunnels     →    true speeds by gradient/surface
   constraints    hard safety rules
```

Almost nothing is written by hand: the left column is extracted from open data, and the right is
measured. That is why 23 circuits is tractable rather than 23 days of tracing — and why the
system has a working frame of reference on day one at a venue nobody has walked yet.

Two rules follow:

- **Everything in the refined column carries a confidence and a sample count.** An edge observed
  by nine traces is not an edge observed by nine thousand, and the routing engine must know the
  difference.
- **Both columns are generated artefacts.** They are written back to the pack, versioned, and
  never hand-edited — the same discipline as `circuits/index.yaml`.

## 2. Pack vs Skill

```
circuits/silverstone/
├── pack/              DATA       loaded by simulator, state, routing
│   ├── circuit.yaml      identity + frame        f1-circuits
│   ├── track.geojson     track outline           f1-circuits
│   ├── constraints.yaml  hard safety rules       authored, small
│   ├── graph.yaml        paths + barriers        OSM      → refined
│   ├── gates.yaml        entry / exit points     OSM      → refined
│   ├── viewing.yaml      grandstands, GA         OSM + venue map → refined
│   ├── crossings.yaml    bridges, tunnels        OSM + event profile → refined
│   └── sensing.yaml      positional accuracy     measured
└── SKILL.md           KNOWLEDGE  loaded by the Crowd Ops Agent
```

**The pack is walked by deterministic engines. The skill is read by a language model.**
Never move graph data into the skill — that puts a routing graph behind an LLM.

The schemas below describe the *shape* of each file. Whether a value was imported from OSM or
later corrected by observation does not change how the engines consume it.

## 3. Pack contents

### `circuit.yaml` — identity and frame

```yaml
id: silverstone
source: gb-1948                 # f1-circuits dataset id
name: Silverstone Circuit
track_length_m: 5891
altitude_m: 196
coordinate_frame:
  origin: { lat: 52.063513, lon: -1.024286 }   # bbox SW corner = venue (0,0)
  rotation_deg: 0
  track_bounds: { x: [0, 1028], y: [0, 1705] } # metres, derived from source bbox
  venue_bounds:  { x: [-900, 1900], y: [-700, 2400] }
```

Every value above except `venue_bounds` is derived from the source GeoJSON, not estimated —
`bbox` gives the corners, `properties.length` the track length. Deriving the frame from the
data is what makes `circuit validate` meaningful.

**`track_bounds` is not `venue_bounds`.** The track occupies roughly 1.0 × 1.7 km; the
spectator envelope — car parks, campsites, park-and-ride, fan zones — is several times that and
extends outside the circuit on every side. The graph lives in `venue_bounds`. Sizing the frame
to the track is a mistake that silently clips every arrival route.

All internal geometry is in the local x/y frame (`plan.md` §10). Lat/lon appears only here and
at the phone's location adapter.

### `graph.yaml` — zones and edges

```yaml
zones:
  - id: gate_a_forecourt
    type: gate            # gate | concourse | crossing | viewing | amenity | exit
    position: { x: 120, y: 340 }
    capacity: 1800

  - id: concourse_north
    type: concourse
    position: { x: 480, y: 360 }
    capacity: 4200

edges:
  - id: e_gate_a_north
    source: gate_a_forecourt
    destination: concourse_north
    distance: 360
    max_capacity: 900        # people per minute
    average_speed: 1.3       # m/s free-flow
    gradient: 0.0
    bidirectional: true
```

`ZoneNode.type` drives behaviour: gates are sources, viewing areas are scheduled attractors,
exits are sinks, crossings are time-gated.

### `gates.yaml` — entry and exit points

```yaml
- id: gate_a
  zone: gate_a_forecourt
  role: entry_exit          # entry | exit | entry_exit
  throughput_per_min: 750
  feeds_from: [park_and_ride_north, shuttle_bay_1]
  opens_offset_min: -240    # relative to first session
```

Different circuits are fed by different transport mixes — rail, park-and-ride, shuttle, walking
— and that mix shapes the arrival curve as much as the gate count does.

### `viewing.yaml` — where people actually go

```yaml
- id: grandstand_club
  zone: viewing_club
  kind: grandstand          # grandstand | general_admission
  capacity: 8400
  sightline: [turn_15, turn_16, pit_straight]
  egress: [concourse_east, crossing_club]
  fill_profile: seated      # seated | roaming
```

Viewing areas are **demand attractors**, not just polygons. They are why people move, and their
egress paths are where the post-session surge lands.

### `crossings.yaml` — the bottleneck mechanism

```yaml
- id: crossing_club
  zone: crossing_club_bridge
  kind: bridge              # bridge | tunnel | at_grade
  connects: [concourse_east, viewing_club]
  throughput_per_min: 420
  availability:
    always_open: true       # bridges and tunnels are not session-gated

- id: crossing_farm
  zone: crossing_farm
  kind: at_grade
  connects: [concourse_north, infield_ga]
  throughput_per_min: 900
  availability:
    always_open: false
    open_when: [between_sessions, pre_session, post_session]
    closed_when: [session_live]
    close_lead_min: 10      # closes 10 min before cars run
    reopen_lag_min: 5
```

At-grade crossings close whenever cars are running. Bridges and tunnels do not — but they have
far lower throughput, which is why they become the pinch point exactly when the at-grade
options shut.

### `constraints.yaml` — hard rules for this circuit

```yaml
one_way:
  - { edge: e_tunnel_south, direction: outbound_only, when: post_session }
accessible_routes:
  - { from: gate_c, to: viewing_hamilton, via: [ramp_east] }
never_route_through: [pit_lane_access, marshal_post_7]
emergency_exits: [exit_e1, exit_e3, exit_e7]
```

`never_route_through` and `emergency_exits` are consumed by the safety engine (§34) as hard
constraints, not preferences.

### `sensing.yaml` — where positioning degrades

```yaml
- zone: tunnel_section
  gnss_quality: none
  fallback: imu_dead_reckoning
- zone: woodland_walk
  gnss_quality: degraded
  accuracy_m: 25
```

This feeds the confidence model (§36) directly: the system reports *lower confidence* in a
tunnel instead of reporting garbage confidently. Monaco's tunnel and Monza's tree cover are the
canonical cases — declaring them is free accuracy in the confidence layer.

## 4. `SKILL.md` — the agent's playbook

Circuit-specific operational knowledge, prose, for the Crowd Ops Agent. This is `plan.md` §39
agent memory given a home.

```markdown
# Silverstone — Operational Notes

## Known bottlenecks
- Club crossing saturates 8–12 min after any session ends; bridge throughput
  is roughly half the at-grade crossing it replaces.
- Woodland Walk backs up in wet conditions — surface slows walking materially.

## Historical interventions
- Holding 20% of Gate A arrivals toward the north concourse flattened the
  pre-race peak without measurably increasing walk time.

## Local constraints worth knowing
- Infield GA is only reachable via at-grade crossings. Once sessions start,
  that population is effectively committed until the next window.
```

The agent reads this to *explain and recommend*. Every recommendation still passes the safety
engine before it becomes an action.

## 5. Circuit vs Event — keep them separate

Geography is static. The timetable is not.

| Circuit Pack | Event Profile |
|---|---|
| `circuits/silverstone/pack/` | `events/2026-british-gp.yaml` |
| Gates, graph, crossings, viewing | This weekend's sessions |
| Changes when the track is rebuilt | Changes every event |

```yaml
# events/2026-british-gp.yaml
circuit: silverstone
sessions:
  - { id: fp1,     start: "2026-07-03T12:30", end: "13:30", kind: practice }
  - { id: quali,   start: "2026-07-04T16:00", end: "17:00", kind: qualifying }
  - { id: support, start: "2026-07-05T11:15", end: "12:00", kind: support_race }
  - { id: parade,  start: "2026-07-05T13:30", end: "14:00", kind: non_track }
  - { id: race,    start: "2026-07-05T15:00", end: "17:00", kind: race }
  - { id: podium,  start: "2026-07-05T17:05", end: "17:25", kind: ceremony }
gates_open: "2026-07-05T09:00"
```

This drives event-aware prediction (`plan.md` §40). The podium ending is the textbook mass-egress
trigger — the system should be pre-positioning before anyone stands up.

Session state also drives crossing availability, which is why the event profile is an input to
the graph, not just to the predictor.

## 6. Time-gated routing

```
session state changes
        │
        ▼
rebuild graph  ──  crossings open/close, one-way rules flip
        │
        ▼
recompute edge costs  (per tick, as normal)
        │
        ▼
candidate path found
        │
        ▼
ETA check: is every edge still open when the walker reaches it?
        │
        ├── no  ──► reject candidate
        └── yes ──► valid route
```

Hackathon scope: rebuild-on-session-change plus the ETA rejection. Full time-dependent shortest
path is a nice-to-have and is not required for the demo.

## 7. Validation

A pack must fail loudly at load, never silently:

```
crowdflow circuit validate silverstone
crowdflow circuit render  silverstone --out silverstone.svg
crowdflow circuit stats   silverstone
```

Checks worth having:

- every edge references existing zones
- every viewing area has at least one egress path
- every gate reaches at least one exit
- capacities are positive; throughputs are non-zero
- `emergency_exits` are reachable from every viewing zone
- no zone is orphaned from the graph

Catching a malformed pack in a linter beats discovering it as a NaN inside the routing engine.

## 8. Scope

**One deep, one shallow.**

| | Purpose | Effort |
|---|---|---|
| Circuit 1 | Fully modelled, tuned so congestion emerges on cue in the demo scenario | Days |
| Circuit 2 | Loads, renders, routes. Proves the format generalises | ~2 hours |

On stage the second circuit is ten seconds — *"same system, different circuit"* — and buys
disproportionate credibility.

For circuit 1, prefer **sprawling over street**: open sky means GNSS alone is sufficient, crowd
movements are large and legible on a heatmap, and there is no hand-modelling of balcony access.
Street circuits are the better story but cost far more per unit of demo.
